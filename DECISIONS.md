# DECISIONS

Architectural decisions, newest first. Each entry records what changed, why this approach over the alternatives, and what I took from it.

---

### 2026-10-23 — LLM provider: Claude → OpenAI gpt-6-luna for both agents; provider-agnostic model builder
**What:** Classifier and synthesizer both default to `openai:gpt-6-luna`. A single `build_model()` (`app/agents/llm.py`) routes a `provider:model` setting to `OpenAIResponsesModel` or `AnthropicModel`, so switching back is an env change rather than a code change. Providers are cached per API key, so both agents share one HTTP connection pool. Trigger: the Anthropic account ran out of credits and every synthesis call returned 400. The pipeline caught each failure, fell back to raw headlines, and still reported `status=completed`, so the site showed 18 cards with no summary or so_what. Also fixed in `metrics.py`: cached tokens were billed twice, because PydanticAI's `input_tokens` already includes `cache_read_tokens`. That didn't matter on Claude, where nothing was cached, but OpenAI auto-caches about 85% of our input, so run cost would have been overstated by about 2x.
**Why this approach:** Measured on the 50-article classifier eval, luna costs about $0.00016 per article, against about $0.0030 for Haiku on the last real run, so roughly 18x cheaper. Most of the gap comes from luna's $0.10/$0.50 list price plus automatic prompt caching (cache reads billed at 0.1x); Claude never cached because our prompt is below its minimum cacheable length. Quality is a little lower but still passes every target: noise precision 0.96 → 0.91 (target ≥ 0.90), recall 0.92 → 0.83 (≥ 0.75), domain accuracy 0.92. The baseline isn't perfectly even, because the prompt was tuned against Haiku. Each luna call takes about 2.9s against about 1.1s for Haiku, which adds roughly 13 minutes to the rate-limited classify stage. Using Chat Completions failed live: gpt-6-luna rejects function tools while reasoning is on, and PydanticAI's structured output depends on tools. The Responses API is OpenAI's path for reasoning models, so that's what the builder uses. Using one tier for both agents reverses the earlier "tier by volume × stakes" split. That's acceptable for now because all 18 backfilled cards came back well grounded. If cards read weaker, set `SYNTHESIS_MODEL=openai:gpt-6-sol`.
**Takeaway:** Provider lock-in belongs at the model-construction boundary, so isolate it there, and re-run the eval before trusting a swap: here it showed a small, measured quality cost in exchange for an 18x price cut. The incident also taught a lesson: graceful degradation (falling back to headlines) hid a total outage, because nothing alerted when the synthesis success rate hit 0%.

### 2026-09-13 — Stories close after a week; headlines rewrite when a story grows
**What:** `open_clusters` (`clustering.py`) keeps a cluster joinable only while `now - min(member_times) <= cluster_window_hours` (168h, `config.py`), measured from each cluster's **earliest** member, so the pipeline's cluster stage now clusters new articles against `open_clusters(existing, ...)` instead of every active cluster. `resynthesize_clusters` (`worker/pipeline.py`) re-runs Sonnet on any cluster that gained members this run, from its 8 newest articles (`fetch_resynthesis_inputs`, newest-first), and writes the new title/summary/so_what over the old ones. One-off `scripts/resynthesize_clusters.py --write` rewrote all 13 then-active clusters, at roughly $0.03-0.04 each; the two magnets it fixed (before → after): "Anthropic launches Claude Opus 5 and cloud-hosted Managed Agents..." → "GPT-6 Astra Launches as OpenAI's Biggest Release, Shadowed by Agent Collusion Incidents and Monitorability Concerns", and "NVIDIA Acquires HuggingFace for $13B as Z.ai's GLM-5.3-Flash Challenges Frontier Coding Models" → "Z.ai's GLM-5.3-Flash Reaches Open-Model Frontier via Post-Training Alone, Running on Chinese Chips".
**Why this approach:** After the previous entry's publication-date fix, the #2 card by momentum still read "Anthropic launches Claude Opus 5" while none of its recent members were about that launch — a Simon Willison quote, an AINews roundup, a Codex interview and a GPT-6 Astra newsletter had all joined it, because each shared a broad entity (a lab name) with the cluster and nothing capped how long a cluster could keep absorbing coverage. **Earliest member, not newest:** windowing from the newest member would let every join refresh the cluster's own deadline, so a magnet would never close — it has to be measured from the event the cluster actually started as. This reverses the 2026-06-21 "new-clusters-only v1" decision, which deferred re-synthesizing updated clusters as future work; that deferral is what let headlines freeze at whatever the first run saw while the cluster's content kept changing underneath it. The 8-article cap bounds cost: an unbounded resynthesis on a 19-member cluster would send roughly 76k characters to Sonnet on every run it gained even one member. Rejected tightening the entity-similarity threshold before re-running the clustering eval — the existing plan already says let the eval decide that, and this bug was a lifetime problem, not a threshold problem: a magnet forms even at the current thresholds if nothing ever stops a cluster from accepting members. Also rejected marking the two bad clusters stale by hand — it fixes today's page and not the mechanism, so the next magnet forms the same way.
**Takeaway:** Ranking by publication date should have sunk every old story, and one didn't, because it wasn't actually old: it kept absorbing new coverage that had nothing to do with what it was originally about. The fix treats a news event as something with a lifetime rather than an open-ended bucket, and measures that lifetime from when the story started, not from whenever it was last touched; otherwise the thing generating the bug also defeats the fix for it.


### 2026-09-13 — Momentum ranks by publication date; weekly decay defaults; news feeds brought back
**What:** `fetch_active_cluster_arrivals` (`cluster_store.py`) now returns each member's `min(articles.published_at, cluster_articles.added_at)`, falling back to `added_at` alone when `published_at` is null — one function change, picked up automatically by `momentum.py`'s scorer and by `worker/pipeline.py` / `scripts/score_momentum.py`, both of which already only take a list of times. `momentum_stale_hours` 48 → **168**, `momentum_half_life_hours` 24.0 → **72.0**, keeping the stale-cutoff-at-two-half-lives relationship the 2026-06-25 entry established (0.5^(168/72) ≈ 0.20, was 0.25). Rescored the live DB: **25 active clusters before → 13 active after**; the 12 that flipped to stale were blog archives whose only live signal had been an `added_at` from the run that first ingested them, months after `published_at`. Four RSS feeds added (measured 7-day entry counts): Google News AI search (85), TechCrunch AI (19), Ars Technica AI (12), The Decoder (10, tied with The Verge's 10 — broken toward The Decoder on a more recent newest-entry timestamp). RSS feed count 18 → 22; total sources (incl. Hacker News) 19 → 23.
**Why this approach:** Reverses 2026-06-25's choice of `added_at` over `published_at`: that call was correct when every feed was same-day news and `published_at` was "nullable, and can be a stale RSS backfill," but once the corpus grew to include long-form blog archives, ingest time stopped meaning event time — a blog's first-ever fetch backfilled years of posts that then scored as breaking news, which is the bug that motivated this whole pass. `min()`, not a straight swap to `published_at`, because the *reason* `added_at` was originally preferred (feed date bugs) is still real — `min` keeps a bad publish date from ever making an article look fresher than the pipeline actually saw it, while still fixing the archive case. Also reverses 2026-08-02's "rejected adding news feeds back": that call was right given the retrieval-corpus deliverable at the time, but running with blogs alone meant the front page stopped doing the one job a briefing feed has — showing the week's actual events — because single-publisher long-form posts don't cluster. News and blogs now both stay, for different jobs (grouping vs. retrieval text). Weekly defaults follow directly from the ingest cadence being weekly (GitHub Actions), not the 48h/24h pair sized for a cadence that no longer exists. The ingest run itself was left out of this entry — it has not happened yet; the numbers above are from the dry-run/rescore script only.
**Takeaway:** A bug found by looking at the product, not the code — the front page showed a months-old model launch above last week's news, and the cause traced to one timestamp being used for two different meanings (arrival vs. event time). The fix was small because the scoring and staleness functions were already pure `(data, knob) → float`/`bool` — swapping what feeds them changed nothing about how they work, which is the payoff of having kept momentum a pure scorer back in June.


### 2026-09-13 — Deploy: one Vercel project with Services, API under `/api` in code, same-origin fetch
**What:** Watcher deploys as a single Vercel project using Services: Next.js at `/` and FastAPI at `/api/*`, routed by a committed `vercel.json` whose rewrites send `/api/(.*)` to the API service and everything else to the frontend. The FastAPI routers are mounted under `API_PREFIX = "/api"` in `app/main.py`, and the frontend calls a relative `NEXT_PUBLIC_API_BASE_URL=/api`, which `fetchJson` resolves against `window.location.origin`. The worker stays on GitHub Actions.
**Why this approach:** The first deploy looked finished and was entirely fake. `NEXT_PUBLIC_*` values are inlined at build time, none were set, so `USE_MOCKS` resolved true and every visitor got `fixtures.ts`; underneath that, the API service had no public route at all, because a service only receives traffic through a top-level rewrite and no `vercel.json` existed, so every candidate API path returned the Next.js 404 page. The diagnosis came from the compiled bundle and the request logs, where detail routes were human-readable fixture slugs like `cursor-series-c` instead of UUIDs. **Why the prefix lives in code:** Vercel passes the original path to the service unstripped, so `/api/clusters` reaches FastAPI as `/api/clusters`. Adding the rewrite alone would have turned every request into a FastAPI 404, and routing into a service is final with no fallback. A platform `request.path` transform would also work, but it would make local and production serve different paths and hide that behaviour in a config file; putting the prefix beside the routes keeps both environments identical and visible where the routes are defined. **Why same-origin:** it removes CORS from production entirely and lets a preview deployment call its own API instead of production's, while resolving a relative base against the page origin keeps the absolute `http://localhost:8000/api` working in development. Rejected two separate Vercel projects (two dashboards, cross-origin CORS, and a frontend pinned to one backend URL so every preview would read production data) and an explicit per-route rewrite list (duplicates the FastAPI route table in config, where it drifts silently). Tradeoffs owned: env vars are shared across services in one project, so the Next.js build environment can see the Supabase secret; only `NEXT_PUBLIC_*` reaches the browser, verified against the deployed bundle, but least privilege is weaker than with two projects. And the 2026-07-03 rate-limit entry's premise that in-memory storage "is fine for one instance" no longer holds: the API runs on Fluid compute and scales out, so slowapi counters are per-instance. At portfolio traffic that is acceptable; Upstash Redis is the fix if it ever is not.
**Takeaway:** The first deploy looked done and was not: the page rendered perfectly and every card was a fixture. I found it by reading the compiled bundle and noticing the request logs were full of fixture slugs rather than UUIDs, then found the API itself had never been routed. I kept `/api` in the application instead of stripping it at the edge because the platform does not strip it, so either the app or the config has to know, and I would rather the path live next to the routes than inside a rewrite rule nobody reads when debugging.

### 2026-09-13 — Embedding-window probe: refuted, and in the opposite direction from the hypothesis
**What:** Hypothesised that embedding truncation (`embedding_max_content_chars` was 2000 while the corpus median moved to 10k-21k chars), not solely the entity-anchored merge rule, drove the publisher-digest clustering regression. Pre-registered a decision rule (recorded in `backend/scripts/probe_embedding_window.py`) before running anything: CONFIRM at balanced mean Δ_within ≤ −0.03, REFUTE at ≥ −0.01. Measured on the live corpus (`backend/scripts/probe_embedding_window.py`, 136 qualifying articles across 9 publishers): **balanced mean Δ_within = +0.0577**, D = −0.0003, only 20.5% of within-pairs negative, **0 of 9 publishers negative**. Refuted — and not merely flat: the sign is opposite the hypothesis. Widening the embedding window from 2000 to 8000 characters *increases* within-publisher cosine similarity, it does not reduce it.
**Why this approach:** Raw within-publisher cosine is confounded by shared subject matter — AWS posts really are about similar things — so a difference-in-differences design was used instead: Δ_ij = cos_8000(i,j) − cos_2000(i,j), where topic similarity appears in both arms and largely cancels. Both embeddings went through the real `format_embedding_input`, with `settings.embedding_max_content_chars` monkeypatched between windows rather than reimplemented, so the measurement used the exact production path. **Why the result likely inverted:** 111 of 136 qualifying articles (82%) are over 8000 characters, so for most of the corpus *both* windows still truncate — the wide arm just sees more of the same document, not the whole thing. Past the boilerplate intro, a publisher's later paragraphs apparently carry more of its house style and vocabulary, not less, so widening the window picked up *more* publisher-specific signal, not a topic-differentiated one. The entity-anchored merge rule (`clustering.py:41`) remains the standing, unmodified explanation for the clustering regression. The embedding-window change ships anyway, on grounds independent of clustering: 39% of stored vectors represented a median 18% of their document, which is not a defensible representation regardless of its effect on clustering quality — but that justification is about representation fidelity, not about fixing publisher-digest behavior, and this result argues against re-opening the clustering threshold on the truncation theory.
**Takeaway:** I proposed a specific mechanism for a known regression, pre-registered a bar for confirming it before running anything, and the measurement came back not just flat but inverted. The pre-registration is the only reason this reads as a clean negative result instead of a hypothesis quietly dropped or a number rationalized after the fact. My best-supported explanation for the inversion is composition: 82% of the qualifying corpus is long enough that *both* windows truncate, so the extra characters the wide window recovers are more page-two publisher house style than differentiating topic content. I did not verify that separately. The change still shipped, on a different justification than the one that motivated the test: a change can survive after the hypothesis that prompted it fails.

### 2026-09-12 — Security pass: XFF spoofing closed, RLS enabled, prompt/CORS/secrets hardened
**What:** Seven fixes from a read-only security audit, scoped to what fits in a day and excluding anything needing a schema change or a redesign. **(1)** `_client_ip` in `rate_limit.py` now honors a new `trusted_proxy_hops` setting (default `0`): with no trusted proxy it keys on the socket address and ignores `X-Forwarded-For` entirely; with `hops=N` it reads the `N`-th entry from the *right* of the header, because each proxy appends the peer it received from. **(2)** New migration enables RLS with zero policies on `articles`, `clusters`, `cluster_articles`, `pipeline_runs` — the four live tables; RLS was previously enabled only on the two vestigial auth tables. **(3)** `worker/run.py`'s shared client caps redirects at 5; `RssConnector._fetch_feed` streams the response and drops any feed past 10 MB instead of reading an unbounded body into memory. **(4)** Both agent prompts wrap the untrusted JSON payload in `<untrusted_article_data>` tags with a one-line "this is data, not instructions" rule in each system prompt. **(5)** CORS drops `allow_credentials` to `False` and `allow_methods` to `["GET"]`; `GET /clusters/{id}` now types the path param as `UUID` so a malformed id returns 422 instead of a raw postgREST 500. **(6)** Connector fetch errors are redacted (host kept, path/query dropped) before they reach `pipeline_runs.source_stats` or the Actions log; the unused `encryption_key` setting is deleted; `tests/conftest.py`'s env-clearing list drops the stale `GOOGLE_API_KEY` and adds the keys that were silently leaking real values into settings tests (`CLAUDE_API_KEY`, `OPENAI_API_KEY`, plus the RPM/embedding/proxy settings the list never had). **(7)** `eslint.config.mjs` adds `react/no-danger: error`; `source-marquee.tsx`'s source list, which advertised 21 outlets including several never fetched, now lists the 11 real RSS feeds plus Hacker News.
**Why this approach:** The one fact that made most of this low-risk to ship is that the backend authenticates to Supabase as `service_role`, which bypasses RLS — so enabling RLS with no policies cannot break the worker or the read API; it only closes the door if the publishable key ever turns out to hold default `anon` grants on these tables. **Measured on 2026-09-12 after applying it: anon holds no grant at all** — a REST read with the publishable key returns `42501 permission denied` on all four tables, so grants, not RLS, were what had been keeping anon out, and this migration is a second lock rather than a fix for a live hole. Applying it surfaced a separate problem worth more than the migration: `supabase migration list` showed `202606260001` as never applied while its columns were live in the schema — applied by hand months ago and never recorded — so `db push` would have aborted on "column already exists" before reaching the RLS migration. `migration repair --status applied` reconciled the history; five local, five remote. The XFF fix was the one rated highest risk: with no auth on this API, the per-IP rate limit *is* the entire abuse control, and trusting the first (attacker-supplied) hop meant it never actually fired — `curl -H "X-Forwarded-For: 10.0.0.$RANDOM"` got a fresh bucket every request. Counting from the right instead of the left is what makes spoofing inert: an attacker can prepend fake hops, but cannot make the proxy's own append land anywhere but the true rightmost position. Prompt isolation and CORS are both "cheap now, expensive as an incident" fixes: no delimiter today means a future markdown renderer or a `CORS_ORIGINS=*` deploy shortcut turns a latent gap into a live one, and the fix is a few lines either way. Left out on purpose: the classifier/synthesizer content truncation (a cost tradeoff, not a security one — see the entry above), output-side grounding checks on synthesized cards (belongs with the retrieval work), and the `user_preferences`/`user_keys` table drop (dead-surface sweep, tracked separately). Test budget was capped at "does this still pass if I delete the fix?" — six tests added (XFF x2, oversized-feed drop, prompt delimiter, malformed-UUID 422, URL redaction), for a suite that went 120 to 126; the RLS migration and the lint rule have no pytest equivalent and are verified by running the API/worker and by manually triggering `dangerouslySetInnerHTML` once.
**Takeaway:** Abuse control on a public, no-auth API is a per-IP rate limit, and it was trivially bypassable via a spoofed `X-Forwarded-For` until this pass, because trusting the first hop only works when a proxy you control is the one writing it. RSS bodies and HN text reach two agents with no isolation; the fix is a delimiter plus an explicit "data, not instructions" rule, with structured output as the actual blast-radius cap. Output-side checking is still open. I assumed RLS was what kept anonymous reads out of my tables, then tested it with the public key instead of reasoning about it, and the error said anon had no grant at all, so the control I thought was load-bearing had never been doing the work. I shipped it anyway as a second lock; the honest framing is defence in depth, not a patched vulnerability. Applying it also uncovered that my migration history claimed a migration had never run while its columns were live in production, so `supabase/migrations/` had quietly stopped being the source of truth it is presented as. RLS has zero policies because nothing legitimate should reach these tables except through the service-role key; a policy that let `anon` read would reintroduce the access this migration exists to remove.

### 2026-09-12 — Truncation ceilings: raised the embedder's, declined the classifier's
**What:** `embedding_max_content_chars` 2000 -> **8000** (`app/core/config.py`). `_MAX_CONTENT_CHARS = 4000` in `classifier.py` and `synthesizer.py` **stays**. Both were unexamined constants that only started binding when the feed swap moved the corpus from a 162-char median to full-text engineering posts at 10k-21k chars — the `rss.py` content fix made its own twin worse, because the text it recovered was being thrown away one stage later.
**Why this approach:** The window is a different decision at every stage, because the price per token differs by two orders of magnitude across the three models in one pipeline: `text-embedding-3-small` is **$0.02/MTok**, Haiku **$1/MTok**, Sonnet **$3/MTok**. Re-embedding the whole 274-document corpus at the wider window costs about **three cents** and ~$0.01/run; raising the classifier's window to full text costs roughly **+$0.75/run**, and the same change at synthesis roughly **+$0.50/run**. On a portfolio project with a real spend limit those are opposite answers, and one policy across all three stages would have been the expensive mistake. **8000, not the model's ~30k limit:** 4x the old window is enough to clear the boilerplate intro that was making vectors similar within a *publisher* rather than within a *subject* (AWS posts all open the same way), but a single 768-dim vector over a 21k-char document averages toward mush — that is the problem chunking solves, and a wider window is not a substitute for it. **The declined arm is the load-bearing one:** the first 4,000 characters carry the topic and the named entities, which is all the classifier is asked to produce, so full text doubles the dominant cost line for no measured gain. Reopen it only on a measured case where `key_entities` misses a subject that appears late in a post and a merge is lost as a result — the clustering eval could measure that and has not. Tradeoff owned: the embedding change applies to **newly-ingested rows only** (`insert_articles` upserts with `ignore_duplicates=True`), exactly like the `rss.py` fix, so the 274 existing articles keep their 2,000-char vectors until a re-embed backfill runs — which means the clustering eval must not be re-run before that backfill, or it tunes a threshold against stale vectors. **The larger lever is still unpulled:** the classifier system prompt is ~2,500-3,000 tokens resent on every call, so at 185 articles roughly 460k tokens of static prompt sit against roughly 185k tokens of article — more than half of classifier spend is the same prompt repeated. The earlier decision to skip prompt caching was about padding a *short* prompt up to the cacheable floor; the prompt has since grown past it, and cache reads bill at 0.1x.
**Takeaway:** Control cost per stage, not globally, because the price per token across my three models differs by 150x, so the same "send more text" change costs three cents at one stage and doubles the bill at another. I priced each change first: the embedder gains real signal for a cent, while the classifier gains nothing I can measure for +$0.75 a run. The biggest remaining cost is not the articles but the system prompt, which is resent on every call and outweighs the content two-to-one, so caching is a bigger lever than anything changed here.

### 2026-09-12 — A crashed run now leaves a row, and the crash that prompted it can no longer happen
**What:** `run_pipeline` accumulates its counters into a mutable `_RunProgress` as the run proceeds and wraps its body: on an exception it builds a `status='failed'` summary carrying `error_message` and the counts reached, persists it through `_record_run`, and re-raises. Paired: `cosine_similarity` now guards its denominator and returns **0.0** for a zero vector instead of raising `ZeroDivisionError`. Two of the three arms of the `pipeline_runs.status` CHECK constraint are now reachable; `'running'` stays unwritten deliberately.
**Why this approach:** `PipelineRunSummary` was constructed once, after every stage had already succeeded, so a run that died partway wrote **nothing at all** — the table that exists to make runs auditable was structurally incapable of recording a failure, and the history it held was a survivorship-biased sample of the runs that worked. Not hypothetical: the 24-minute run lost to shell teardown on 2026-08-02 burned ~$0.07 and left no trace. **`_record_run` swallows its own errors** because on the failure path the pipeline's exception is the diagnostic worth propagating and a lost audit row must not mask it — the bookkeeping failure is the less interesting of the two. **`'running'` stays unwritten** because the worker is a one-shot: there is no window in which anyone would observe a row mid-run, so a running state would be a row nobody reads. **The test asserts the partial counts survive, not that a row appears** — the same lesson as the `in.()` batching regression test, because the natural assertion ("a failed row exists") still passes if you delete the counters, so the assertion has to sit on the thing the fix actually added; a second test asserts the original exception still propagates when the audit write also fails. The zero-norm guard belongs in this entry because it closes the loop from the other end: it was the most likely source of a mid-run crash, and **0.0** is the right return because a zero vector has no direction and so is similar to nothing, which keeps the article out of every merge rather than ending the run. Rejected raising on a zero vector (defensible in the abstract, but it converts one bad embedding into a dead run) and rejected filtering zero vectors upstream (pushes the same decision into a stage with less context). Known gap left open: an article whose classification *failed* is still stored indistinguishable from one classified as non-noise with zero relevance, because the row falls back to the DB defaults — separating the two needs a schema change and belongs to the migration that makes it.
**Takeaway:** I could not tell whether the pipeline was healthy: my run table had a `failed` status arm that no code path ever wrote, so the only runs I could see were the ones that succeeded. The test asserts on the partial counts rather than on the row existing, because the natural assertion passes with the fix removed; that is the second time in this repo the useful test was the one that could actually fail.

### 2026-09-12 — One content format behind the connector protocol
**What:** `clean_html` moved out of `rss.py` into `app/services/html_text.py` and is now used by both connectors — HN's `text` field was being stored as raw HTML while RSS bodies were stripped. Paired: `rss.py` reads `entry.get("published") or entry.get("updated")` instead of `published` alone.
**Why this approach:** `ArticleConnector` promises one normalized `ArticleInput`, and two connectors producing `content` in two different encodings quietly breaks that promise everywhere downstream — `<p>` tags and `&#x27;` entities were being paid for in every Ask HN classifier prompt and embedded as though they were text. Extracted rather than copied, because the repo already carries a flagged duplication problem (`_trim_text` is byte-identical in `classifier.py` and `synthesizer.py`) and adding a third copy of a helper to fix a contract bug trades one smell for another. **On the date:** feedparser's aliasing is one-directional — `FeedParserDict` maps `updated` -> `published` when `updated` is missing, never the reverse — so an Atom entry carrying only `<updated>` silently produced a null `published_at`. Reading `published` first is deliberate rather than stylistic: `.get` routes through the overridden `__getitem__`, so the reverse order would trigger feedparser's deprecated fallback and a warning on every entry. Whether any live feed was actually affected is still unmeasured; the fix was cheap enough that it did not wait for the measurement.
**Takeaway:** Two implementations of the same interface agreed on the schema and disagreed on the encoding, which type checking cannot catch: one connector's `content` was plain text and the other's was HTML, and the cost surfaced two stages later as prompt tokens and polluted embeddings. I found it by reading the two connectors side by side while auditing for a different bug class entirely.

### 2026-08-02 — Day 1 failure log: the un-batched `in.()` filter, and two operational stops

**What:** Three things failed during the Day 1 feed-swap run. All three are fixed; recorded here because two of them are the kind that only appear at real corpus size.

**1. The pipeline crashed on its first attempt — postgREST 400, "JSON could not be generated".** `fetch_existing_canonical_urls` in `app/services/article_store.py` declared `_IN_FILTER_BATCH_SIZE = 20` with a comment explaining exactly the URL-length overflow it was guarding against — and then never used the constant. It sent all ~280 canonical URLs in a single `in.(...)` filter, producing a ~9 KB request URL that the gateway rejected. postgREST puts `in.()` filters in the query string, so the failure scales with corpus size: the code worked for the entire life of the project and broke the first time the feed swap pushed the URL pool past the limit. **Fix:** iterate `range(0, len(urls), _IN_FILTER_BATCH_SIZE)` and union the results — the loop the constant was written for. Regression test `test_fetch_existing_canonical_urls_batches_the_in_filter` asserts the batch sizes are `[20, 20, 5]` for 45 URLs, so the assertion is on the *chunking*, not just on the returned set.

**2. A 24-minute pipeline run was lost to shell teardown.** The run was launched as a background job of an ephemeral shell; when that shell's parent exited, the run died with it — 17 of 185 classifier calls made, no DB writes (the insert happens only after classification completes), ~$0.07 burned. **Fix:** relaunch under `setsid nohup … < /dev/null & disown` so the process gets its own session and survives the parent. The second run completed: 263 fetched / 185 classified / 16 clusters, 23.6 minutes.

**3. Every Supabase call failed DNS for one stretch.** `httpx.ConnectError: [Errno -3] Temporary failure in name resolution`. The pooler host and the `supabase.co` apex both resolved; only the project subdomain didn't — which is what a paused free-tier project looks like from the client side, not a network fault. **Fix:** the project was unpaused and the queries reran unchanged.

**Why this approach:** On (1), the interesting part is that the guard was already designed and documented and still didn't run — the comment described the bug correctly while the code below it did the wrong thing, so reading the file gave false assurance. That is why the test asserts the observed batch boundaries rather than just "the right URLs came back": a test on the return value alone passes with the batching removed. Rejected raising the batch size to something larger-but-still-safe — the limit is a property of the gateway and the URL lengths, both outside this code's control, so a small fixed batch with an extra round trip per 20 URLs is the cheap correct answer at this corpus size. On (3), the diagnostic worth keeping is that a partial DNS failure — apex resolves, subdomain doesn't — is a *service state* signal, not a connectivity one; treating it as a network problem would have wasted the session.

**Takeaway:** An `in.()` filter had never been batched, because the corpus had never been large enough to overflow the request URL; the guard constant and the explanatory comment were both already in the file, unused. The test asserts on the batch boundaries rather than the result set, because the natural assertion ("the right URLs came back") still passes if you delete the fix. ### 2026-08-02 — Corpus is long-form blogs, not news; the retrieval corpus is defined, and event clustering is given up

### 2026-07-13 — Scheduling: GitHub Actions cron, not a scheduler daemon or systemd timer
**What:** The ingestion pipeline runs from a single GitHub Actions workflow (`.github/workflows/ingest.yml`) on two triggers with identical behavior: `schedule: cron '0 6 */2 * *'` (~every 2 days) and `workflow_dispatch` (a manual "Run workflow" button that doubles as the live-demo trigger). Each run `uv sync --frozen --no-dev`s and invokes the already-one-shot `worker.run`; secrets map to env (`SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `CLAUDE_API_KEY`, `OPENAI_API_KEY`) with `RSS_FEED_URLS` as a repo variable. Paired change: a log formatter in `worker/run.py` that renders the `extra=` payload the stdlib default formatter drops, so each stage's counts (`articles_fetched=… classified=… clusters_created=…`) show up in the run log. `PYTHONUNBUFFERED=1` so logs stream live in the Actions viewer instead of flushing at the end.
**Why this approach:** The worker is already an idempotent one-shot — dedup filters against persisted `canonical_url`s, so reruns and overlapping runs are safe — which means it needs a *trigger*, not an orchestrator or a long-running scheduler. That reframes the choice: pick the cheapest trigger, not the most capable scheduler. Rejected an **in-process interval loop / APScheduler** (a process you keep alive and babysit, reimplementing missed-run/catch-up logic, to do what a cron trigger does for free); a **systemd timer on EC2** (robust, but the schedule lives in a host unit file outside the repo and requires the box to own scheduling); and **EventBridge Scheduler → Fargate** (the real scale answer, but Lambda's 15-minute cap rules it out for serial rate-limited LLM classification, and Fargate + IAM + VPC egress is overkill for a portfolio POC). GitHub Actions wins on fit: zero servers for the timer, the schedule is **version-controlled in the repo**, it's free/unlimited on a public repo (which a portfolio wants anyway), and `workflow_dispatch` gives a one-click on-demand run whose logs stream in the Actions UI — the demo path and the scheduler are the same artifact. It also cleanly splits the deploy: the worker lives on GitHub runners, so EC2 hosts only the always-on read API and ingestion leaves AWS entirely. Tradeoffs owned: GH cron is best-effort (can lag minutes under load — irrelevant at a 2-day cadence), `*/2` is "odd days of month" so month-end gives one back-to-back pair, and GitHub auto-disables *scheduled* workflows after 60 days of repo inactivity (manual dispatch always fires). The logging wrinkle is the non-obvious one: `logger.info(event, extra={...})` is invisible under the default formatter, so without the custom formatter a "live demo" would show bare event names with every useful number dropped.
**Takeaway:** The worker is an idempotent batch one-shot, so it needs a trigger, not an orchestrator: GitHub Actions on a cron, with the manual-dispatch button doubling as the live-demo trigger. A 7-step linear DAG run every couple of days doesn't need a DAG engine (Airflow, APScheduler, a cron daemon on a box), and a long-running scheduler is a process to babysit for what a trigger does for free; idempotency via dedup makes overlap and reruns safe, so there's no missed-run bookkeeping to own. Off GitHub, I would use EventBridge Scheduler → a Fargate task, not Lambda, because serial LLM calls blow past the 15-minute limit. One detail worth knowing: the stdlib logger drops `extra=`, so making a run legible was a real change, not a config toggle.

### 2026-07-04 — Frontend: client-side fetch (browser → public API), not a server component

### 2026-06-30 — Read API: purpose-built `ClusterCard`, normalization at the read boundary
**What:** The read API returns purpose-built `ClusterCard`/`ClusterPage` models (`app/models/cluster_api.py`), not the DB row or the internal `Cluster`. The store (`fetch_clusters_page`) returns **raw rows + a filtered count** as a tuple; the 0–100 normalization (`100·raw/(raw+k)`, `k=5` via `_MOMENTUM_K`) is a read-time transform in the API layer (the `_row_to_card` mapper) — never in the store, never persisted. The card's `momentum` is the normalized value (`Field(ge=0, le=100)`); raw `momentum_score` stays internal. `status` is a `StrEnum`; `summary`/`so_what` are nullable (synthesis can be absent).
**Why this approach:** Same discipline as `SynthesisInput` — the response is a contract you control, decoupled from storage, exposing only what a card shows and never the centroid (768 floats) or `signal_type`. The store returns `(rows, count)` rather than cards because `total ≠ len(page)` — the count is the filtered total for pagination, which a 20-row page can't supply.
**Takeaway:** The 0–100 normalization lives at the read boundary after a pure DB fetch: storage stays raw/canonical, `k` is tunable without a backfill, and because the map is monotone it doesn't disturb the indexed momentum sort. The API returns a purpose-built response model instead of the row, for contract control, decoupling from storage and hiding the centroid.

### 2026-06-25 — Momentum: recency-weighted decay sum, pure scorer, full DB pass
**What:** `score_momentum(arrivals, now, momentum_half_life_hours=24.0)` in `app/services/momentum.py` — a pure function. Each member contributes `0.5 ** (age_hours / half_life)`; the contributions are **summed** (not averaged). Arrival time is `cluster_articles.added_at` (when a member joined the story), not `articles.published_at` (nullable, and can be a stale RSS backfill). Momentum is recomputed for **all active clusters every run** via a DB pass, not just clusters touched this run. A separate stale flag marks `status='stale'` when the newest member is older than `momentum_stale_hours=48`. Normalization to 0–100 is deferred to the API/display layer (a fixed saturating map `100·raw/(raw+k)` applied at read time): the stored score stays the raw absolute sum, which already sorts via `idx_clusters_momentum` and stays comparable across runs.
**Why this approach:** The defense against "a huge but old story pins the top of the feed" lives in the *shape of the function* (decay), not in *filtering the input*. Because each member's weight halves every 24h, you can safely hand the scorer every member and old ones fade to ~0 on their own — no exclusion logic. **Sum, not mean:** momentum must reward a story that *accumulates* coverage, so the member count has to survive into the score; averaging the weights would flatten "10 fresh articles" and "3 fresh articles" to the same ~1.0 and erase the growth signal. **Pure `(data, knob) → float`:** half-life is a parameter (config-fed at the call site), so the scorer unit-tests without mocking and is defensible on a whiteboard. **Full DB pass, not in-run:** a cluster that received nothing this run still decays and can cross the stale line purely from elapsed time — that transition is invisible to a touched-only pass, so staleness forces sweeping every active cluster. **half-life (24h) < stale window (48h)** by design: at the stale cutoff a member has aged two half-lives and contributes only 0.25, so the score and the stale flag agree instead of contradicting (a 48h half-life would still count a near-dead article at 0.5). **Rejected per-run min-max** (`score / max_this_run`): a cluster's badge would move whenever *other* clusters change, destroying run-to-run comparability and the gaining-vs-fading read — so the 0–100 map is a fixed saturating function at display time, never relative. **Known limitation:** a cluster already marked `stale` is invisible to clustering (which fetches only `active`), so it can't re-absorb new members and revive — a clustering-fetch change left out of momentum's scope.
**Takeaway:** The decay curve sinks old members, the sum rewards fresh accumulation, and the stale cutoff hard-cuts the tail, so a huge but old story cannot pin the top. Clusters that got no new articles are still recomputed, because staleness is a function of elapsed time, not of an ingestion event, and a touched-only pass would never detect a story going cold.

### 2026-06-21 — Synthesis model: Sonnet 4.6 vs Haiku for classification; the env-precedence 404

Shipping bug: `.env`'s `SYNTHESIS_MODEL` still held the old `google-gla:gemini-2.5-flash`, which overrides the `config.py` default — and since the model-name helper only strips an `anthropic:` prefix, that literal string was sent to the Anthropic API → 404 on every synthesis call while the rest of the pipeline succeeded. Fixed the env value and verified live (15/15 clusters synthesized, 0 failures).
**Why this approach:** Synthesis is the quality-critical surface — the one card the user reads — and runs at low volume (a handful of calls per run), so the marginal cost of the stronger model is small. Classification is high-volume (every fetched article), where Haiku's price dominates, so it stays cheap. Model choice tiers by volume × quality-stakes, not one model everywhere.
**Takeaway:** Tier models by volume and quality stakes. Separately, config precedence (env over code defaults) caused a silent 404 that unit tests missed because they mock the LLM boundary.

### 2026-06-05 — Classifier provider: Gemini Flash-Lite → Claude Haiku 4.5
**What:** Swapped the classification agent to Claude Haiku 4.5 (PydanticAI `AnthropicModel`) and trimmed deps to `pydantic-ai-slim[anthropic]`.
**Why this approach:** Gemini's free tier hit a hard requests-per-day (RPD) wall mid-run; prepaid Claude credits give a controllable hard spend cap, and Haiku is cheap enough (~$0.004/article) for a scheduled pipeline. Rejected padding the prompt past 4,096 tokens to force prompt caching — a hack, and caching silently no-ops below Haiku's cacheable floor.
**Takeaway:** The binding constraint was the free tier's requests-per-day wall (RPD, not RPM); prepaid credits give a hard spend cap. Prompt caching did not apply here, and padding the prompt past the cacheable floor to force it would have been a hack.

### 2026-06-05 — Dedup before classify (recurring-cost lever)
**What:** The pipeline filters fetched articles against already-persisted `canonical_url`s *before* the classifier runs, and records the skipped count in `pipeline_runs.articles_skipped_known`.
**Why this approach:** Re-classifying the whole pool every run was the dominant recurring cost; dedup-first only classifies the delta (~4–10× cheaper after the cold first run). Rejected cheaper-model / prompt-trimming as smaller levers that also cost quality. Tradeoff: one extra DB read per run (negligible).
**Takeaway:** The cost lever is *what you send*, not *which model*: filtering against already-stored URLs before the classifier runs cut recurring cost 4–10× without touching quality, where a cheaper model or a trimmed prompt would have been a smaller win that also cost quality.

### 2026-06-05 — Classifier eval: human-labeled fixture + harness
**What:** A 50-article, class-balanced eval fixture with blind human labels, plus `eval_classifier.py` reporting noise precision/recall, domain overlap, and relevance-band accuracy against fixed targets.
**Why this approach:** Tests prove the code runs; an eval proves the *behavior* is correct. Labeled by hand — not by a model — because the classifier is Claude, so labeling with a Claude model would be circular (shared blind spots). Targets are asymmetric (noise precision ≥0.90 > recall ≥0.75) because a false-positive = dropping a good article, the one failure the product can't afford. Domain uses a deliberately lenient overlap metric (can mask over-tagging) since domain is secondary to the noise gate.
**Takeaway:** Ground truth is labeled by hand, not by a model, because grading a model with itself is circular (shared blind spots). The targets are asymmetric (noise precision ≥0.90 over recall ≥0.75) because the one failure the product can't afford is dropping a good article. The domain metric is deliberately lenient and can mask over-tagging; I name that weakness rather than hide it.

### 2026-06-05 — Taxonomy: removed `culture`; signal = insight, not "technical"
**What:** Dropped the `culture` domain and added a noise rule for nostalgia / retro trivia / standalone quotes, so pure low-substance "interesting" items have no home domain and fall to noise.
**Why this approach:** The eval surfaced that the classifier scored low-substance culture items almost randomly (0.15–0.50). Encoding the editorial stance in the *taxonomy* (no bucket ⇒ noise) is simpler and more consistent than a fuzzy scoring rule. The governing rubric: signal = an actionable insight or fresh perspective, not merely "is it technical" — a business-strategy essay with a real thesis is signal; demoscene nostalgia is not. Rejected a culture-IS-signal rule (an initial misread of the rubric that the eval corrected).
**Takeaway:** The eval changed a design decision: it showed the classifier scoring low-substance culture items almost randomly, so I removed the domain and encoded the editorial stance in the taxonomy (no bucket means noise), and the noise definition tightened on real disagreements.
