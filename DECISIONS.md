### 2026-07-13 — Scheduling: GitHub Actions cron, not a scheduler daemon or systemd timer
**What:** The ingestion pipeline runs from a single GitHub Actions workflow (`.github/workflows/ingest.yml`) on two triggers with identical behavior: `schedule: cron '0 6 */2 * *'` (~every 2 days) and `workflow_dispatch` (a manual "Run workflow" button that doubles as the live-demo trigger). Each run `uv sync --frozen --no-dev`s and invokes the already-one-shot `worker.run`; secrets map to env (`SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `CLAUDE_API_KEY`, `OPENAI_API_KEY`) with `RSS_FEED_URLS` as a repo variable. Paired change: a log formatter in `worker/run.py` that renders the `extra=` payload the stdlib default formatter drops, so each stage's counts (`articles_fetched=… classified=… clusters_created=…`) show up in the run log. `PYTHONUNBUFFERED=1` so logs stream live in the Actions viewer instead of flushing at the end.
**Why this approach:** The worker is already an idempotent one-shot — dedup filters against persisted `canonical_url`s, so reruns and overlapping runs are safe — which means it needs a *trigger*, not an orchestrator or a long-running scheduler. That reframes the choice: pick the cheapest trigger, not the most capable scheduler. Rejected an **in-process interval loop / APScheduler** (a process you keep alive and babysit, reimplementing missed-run/catch-up logic, to do what a cron trigger does for free); a **systemd timer on EC2** (robust, but the schedule lives in a host unit file outside the repo and requires the box to own scheduling); and **EventBridge Scheduler → Fargate** (the real scale answer, but Lambda's 15-minute cap rules it out for serial rate-limited LLM classification, and Fargate + IAM + VPC egress is overkill for a portfolio POC). GitHub Actions wins on fit: zero servers for the timer, the schedule is **version-controlled in the repo**, it's free/unlimited on a public repo (which a portfolio wants anyway), and `workflow_dispatch` gives a one-click on-demand run whose logs stream in the Actions UI — the demo path and the scheduler are the same artifact. It also cleanly splits the deploy: the worker lives on GitHub runners, so EC2 hosts only the always-on read API and ingestion leaves AWS entirely. Tradeoffs owned: GH cron is best-effort (can lag minutes under load — irrelevant at a 2-day cadence), `*/2` is "odd days of month" so month-end gives one back-to-back pair, and GitHub auto-disables *scheduled* workflows after 60 days of repo inactivity (manual dispatch always fires). The logging wrinkle is the non-obvious one: `logger.info(event, extra={...})` is invisible under the default formatter, so without the custom formatter a "live demo" would show bare event names with every useful number dropped.
**Interview angle:** "How do you schedule the pipeline?" — it's an idempotent batch one-shot, so it needs a trigger, not an orchestrator; GitHub Actions on a cron, with the manual-dispatch button doubling as the live-demo trigger. Follow-up "why not Airflow / APScheduler / a cron daemon on the box?" — a 7-step linear DAG run every couple of days doesn't need a DAG engine, and a long-running scheduler is a process to babysit for what a trigger does for free; idempotency via dedup makes overlap and reruns safe, so there's no missed-run bookkeeping to own. Follow-up "how would it scale off GitHub?" — EventBridge Scheduler → a Fargate task, not Lambda, because serial LLM calls blow past the 15-minute limit. The sleeper detail: the stdlib logger drops `extra=`, so making a run demo-legible was a real change, not a config toggle.

### 2026-07-04 — Frontend: client-side fetch (browser → public API), not a server component
**What:** `/feed` and `/cluster/[id]` fetch the read API directly from the browser via SWR, keyed on `NEXT_PUBLIC_API_BASE_URL` — not from a Next server component or route handler. Next ships only static shells; all cluster data is client-fetched and typed (`lib/api.ts` `fetchJson` → `ClusterPage`/`ClusterDetail`, with a `RateLimitError` that reads the `Retry-After` header).
**Why this approach:** The backend's per-IP rate limit and its 429-toast requirement both depend on the browser being the client. A server-component fetch routes every user through Vercel's single egress IP, collapsing per-IP into one shared bucket that throttles everyone; and a server-side 429 dies on the server with no browser to surface the "slow down" toast. Client-side fetch preserves each user's real IP *and* lets the 429 reach the browser — one decision satisfies both the per-IP key and the toast. It also keeps the trust boundary clean: the frontend talks only to the public API, never Supabase, so the service key and RLS stay a backend concern. Tradeoff: no SSR/SEO for cluster content and a visible loading state — acceptable for a read-only dashboard where the data is public and the feed *is* the product, not a marketing surface.
**Interview angle:** "Why fetch on the client instead of server-rendering the feed?" — because the API's per-IP rate limiting and its browser-facing 429 toast both need the request to carry the user's real IP and the response to reach the browser; a Vercel server component would share one egress IP and swallow the 429. One constraint (per-IP + toast) dictated the fetch location. (Pairs with the backend rate-limit entry below.)

### 2026-07-04 — Frontend: "Signal cards" editorial feed, not a bento grid or a list
**What:** The feed is an editorial hero layout — the top 2 momentum clusters as large feature cards, the rest as a uniform, content-height card grid — styled as a terminal-intelligence console (monospace metadata + numerals, sans prose, one semantic heat accent per card). Framed honestly as a **daily briefing** ("Updated daily"), not a live monitor, because the pipeline is a once-a-day batch.
**Why this approach:** Started on a fixed-height **bento grid** (tile size encodes momentum); it clipped the variable-length LLM `so_what` on small tiles and left dead space on big ones. Research converged on the rule: bento is for *curated, self-authored* content where you control what fills each box — not a *dynamic feed* of generated text. Rejected the opposite over-correction (a full **list**, which the dev disliked) and landed on the proven news pattern: an editorial hero (size still encodes importance, but only for the lead) plus a uniform grid where content — not a fixed box — sets height, so nothing clips. The console aesthetic is on-brand (the product is literally a monitor named Watcher) and borrows Palantir's *DNA* — functional dark, semantic color, entity-first mono tags — deliberately **not** its density (a multi-panel analyst dashboard would blow POC scope and demo worse than a readable briefing). Honesty on "daily, not live" is a feature: a fake `● LIVE` badge on a batch pipeline is the first thing an interviewer catches.
**Interview angle:** "Walk me through a design decision you reversed." — bento looked great in mockups but clips generated text, because fixed-size tiles assume you author content to fit and a news feed doesn't; the fix was an editorial hero + content-height grid (size-encodes-importance kept for the lead, dropped where it fought the content). Follow-up: "why not go full Palantir dashboard?" — borrow the DNA, not the density; the audience is a 2-minute reader, not an analyst.

### 2026-07-04 — Frontend: momentum as a monospace readout, not a trend line
**What:** Each card renders momentum as a large monospace number on a continuous hot→cool color scale (`hsl` 210°→10° by value) with a slim fill meter — custom SVG/markup, no chart library. Higher momentum also reads through the feature-vs-standard card size and a heat-tinted accent.
**Why this approach:** Momentum is a **level, not a series** — the API exposes a single normalized 0–100 value per cluster, and historical momentum is a post-launch feature (no time buckets are surfaced). A sparkline or trend line would imply a time axis that doesn't exist and fabricate data; a single legible number is the honest encoding, and monospace + heat color makes it the card's anchor (an earlier thin ring read as faint noise across a grid). Rejected a chart library entirely (AGENTS bans D3/charts, and the viz is simple enough to hand-roll as SVG). Tradeoff: less "dashboard-y" than a chart, but it can't misrepresent absent data.
**Interview angle:** "Why not a sparkline for momentum?" — there's no time series to spark; momentum is a scalar level, and a trend line would invent a time axis. The right viz encodes exactly what the data is — a hot-or-cold magnitude — as a number, not a fake trend.

### 2026-07-04 — Frontend security: scope to the actual no-auth surface
**What:** Security targets the real surface of a public, read-only, no-auth page: LLM/feed text (`title`/`summary`/`so_what`/article titles) rendered as **text only** (React auto-escaping — no `dangerouslySetInnerHTML`, no markdown renderer); external links scheme-validated to `http(s)` with `rel="noopener noreferrer"` (`lib/links.ts`); only `NEXT_PUBLIC_API_BASE_URL` exposed to the browser; and CSP + `nosniff`/`Referrer-Policy`/`X-Frame-Options` set in `next.config`. The generic auth/BYOK/Supabase-client checklist items are marked N/A.
**Why this approach:** A no-auth read-only page has no tokens, BYOK keys, or Supabase service key to leak, so most of the generic frontend checklist doesn't apply — pretending it does is theater. The genuine risks reduce to two: **XSS from synthesized/external text** (the `so_what` is LLM-generated; article URLs come from HN/RSS — both untrusted), handled by rendering as text and never adding a markdown/HTML sink; and **unsafe external links** (an attacker-influenced `javascript:`/`data:` URL), handled by a scheme guard + `noopener`. Keeping the frontend talking only to the public API — never Supabase directly — keeps the service key and trust boundary on the backend. Tradeoff: the CSP allows `'unsafe-inline'` for styles/scripts (Next App Router injects inline bootstrap without nonces) — accepted for a POC with no secrets behind it.
**Interview angle:** "How did you secure the frontend?" — by scoping to the actual surface. No auth means no tokens to steal, so the auth/BYOK checklist is mostly N/A; the real risks are XSS from LLM/feed text (rendered as text, never `dangerouslySetInnerHTML`) and unsafe external links (scheme-validated + `noopener`). Security is matching controls to the threat model, not running every checkbox.

### 2026-07-03 — Public read API: in-app per-IP rate limiting (slowapi), client-side fetch to keep real IPs
**What:** The public, no-auth read API is rate-limited in-app with slowapi — a global `SlowAPIMiddleware` keyed per client IP, limit env-driven (`RATE_LIMIT`, default `60/minute`; `RATE_LIMIT_ENABLED` kill switch), key func XFF-aware (first `X-Forwarded-For` hop, for EC2-behind-a-proxy). A custom 429 handler returns JSON `{detail, limit, retry_after_seconds}` plus the standard `Retry-After` / `X-RateLimit-*` headers; `CORSMiddleware` is registered **after** SlowAPI so it stays outermost and the CORS headers land on the 429. The dashboard is specified to fetch **client-side** (browser → API), not via a Next.js server component. Deferred: an optional global cap (`RATE_LIMIT_GLOBAL`) and edge/CDN limiting.
**Why this approach:** No auth means auth can't gate abuse, so a per-IP limit is the DoS/fairness bound — but per-IP only works if the API sees each user's *real* IP. A server-component fetch routes every user through Vercel's single egress IP, collapsing per-IP into one shared bucket that throttles everyone together; client-side fetch preserves the real IP and, as a bonus, lets the 429 reach the browser so the frontend can show a "slow down" toast (a server-side 429 dies on Vercel with no browser to notify). The limit is config, not a constant, so it retunes on a free EC2 without a redeploy. In-memory storage is fine for one instance; Redis + a global cap are the scale path, not POC work. Rejected: edge/CDN limiting (no CDN in front for the POC) and forwarding a trusted client-IP header through Vercel (spoofable without a shared secret — more machinery than a public cards page warrants).
**Interview angle:** "Public API, no auth — how do you stop abuse?" — per-IP in-app rate limit; auth is the wrong tool for DoS. Follow-up: "on Vercel + EC2, doesn't the frontend hide the user's IP?" — only if you fetch server-side; the POC fetches client-side precisely so per-IP stays meaningful and the 429 can surface a toast. The CORS-on-429 middleware-ordering detail is the kind of thing that silently breaks the toast if you miss it.

### 2026-07-03 — Read API: cluster detail endpoint — stale permalinks resolve, 404 only for missing
**What:** `GET /clusters/{id}` returns a `ClusterDetail` (the card fields plus member articles as `ClusterArticleRef`s). The store's `fetch_cluster_detail` fetches the cluster **by id with no `status` filter**, then joins members through `cluster_articles` → `articles`; it returns `None` for an unknown id, which the handler translates to the one deliberate `HTTPException(404)`. A cluster that has gone stale still resolves on its permalink.
**Why this approach:** Visibility is a per-surface decision, not a global one. Hide-stale (below) is a *feed* rule — it keeps the ranked list meaning "live stories." A direct permalink is a different intent: "show me this exact resource," typically reached from a saved or shared link. 404-ing a cluster the moment its momentum decays would rot every outstanding link for no product gain — the row still exists and is still meaningful. So the detail path drops the status filter and reserves 404 for ids that genuinely don't exist. `ClusterDetail` subclasses `ClusterCard` so the JSON stays flat (card fields + `articles`) rather than nested; member articles are a purpose-built `ClusterArticleRef` (id/title/url/source/published_at), never the raw article row or its embedding.
**Interview angle:** "You hide stale clusters from the feed — do you also 404 them on their detail page?" — no; visibility is per-surface. A feed is a curated 'what's live' view; a permalink is 'this specific thing you asked for.' Hiding governs the list, not the resource, so deep links stay stable while the ranked feed stays clean.

### 2026-06-30 — Read API: stale clusters hidden, not shown or ranked-below
**What:** `GET /clusters` filters `status='active'` in the store query (`cluster_store.fetch_clusters_page`), so stale clusters are never served — removed from the result set *and* from the paginated `total` (`count="exact"` respects the filter). Chosen over "show" (decayed clusters linger, still reachable by paging) and "rank-below" (a compound `status`-then-momentum sort for marginal value).
**Why this approach:** A read API's visibility is a product call the query must encode, not a default to inherit from the sort. Momentum decay controls *ordering*, not *membership* — a stale cluster still has a non-zero raw score and would remain reachable under "show." Hiding makes the feed mean exactly "live stories," matching the BUILD_PLAN MVP stance. The cost is owned deliberately: with every current cluster stale (no run since 06-21), the live feed is empty until a worker run — a demo precondition, not something the API should paper over. Stale rows still persist for dedup / RAG / eval; they're just not *served*.
**Interview angle:** "Your feed is already sorted by a decaying score — why also filter stale instead of letting decay bury it?" — decay is ordering, visibility is membership; they're separate decisions, and encoding "current" in the query keeps the served set semantically clean while the data stays intact for other consumers.

### 2026-06-30 — Read API: purpose-built `ClusterCard`, normalization at the read boundary
**What:** The read API returns purpose-built `ClusterCard`/`ClusterPage` models (`app/models/cluster_api.py`), not the DB row or the internal `Cluster`. The store (`fetch_clusters_page`) returns **raw rows + a filtered count** as a tuple; the 0–100 normalization (`100·raw/(raw+k)`, `k=5` via `_MOMENTUM_K`) is a read-time transform in the API layer (the `_row_to_card` mapper) — never in the store, never persisted. The card's `momentum` is the normalized value (`Field(ge=0, le=100)`); raw `momentum_score` stays internal. `status` is a `StrEnum`; `summary`/`so_what` are nullable (synthesis can be absent).
**Why this approach:** Same discipline as `SynthesisInput` — the response is a contract you control, decoupled from storage, exposing only what a card shows and never the centroid (768 floats) or `signal_type`. Normalization belongs at the boundary it serves: out of the store, storage stays canonical (raw absolute — per-run min-max rejected for run-to-run comparability), and `k` becomes a tunable with zero migration. **`k=5`:** `k` is the raw score that maps to a 50 badge; because a fresh member contributes ~1.0 to the raw decay sum, raw ≈ fresh-article count, so `k=5` reads "≈5 articles of live coverage" as a mid-tier story (raw 10→67, 15→75, then a gentle saturating tail). Sorting on raw in the DB (`idx_clusters_momentum`) then normalizing *after* the fetch is safe because `100·raw/(raw+k)` is **monotonic in raw**, so order is preserved. The store returns `(rows, count)` rather than cards because `total ≠ len(page)` — the count is the filtered total for pagination, which a 20-row page can't supply.
**Interview angle:** "Where does the 0–100 normalization live, and why there?" — at the read boundary after a pure DB fetch: storage stays raw/canonical, `k` is tunable without a backfill, and because the map is monotone it doesn't disturb the indexed momentum sort. Follow-up: "why a purpose-built response model instead of returning the row?" — prompt-surface/contract control, decoupling from storage, hiding the centroid.

### 2026-06-25 — Momentum: recency-weighted decay sum, pure scorer, full DB pass
**What:** `score_momentum(arrivals, now, momentum_half_life_hours=24.0)` in `app/services/momentum.py` — a pure function. Each member contributes `0.5 ** (age_hours / half_life)`; the contributions are **summed** (not averaged). Arrival time is `cluster_articles.added_at` (when a member joined the story), not `articles.published_at` (nullable, and can be a stale RSS backfill). Momentum is recomputed for **all active clusters every run** via a DB pass, not just clusters touched this run. A separate stale flag marks `status='stale'` when the newest member is older than `momentum_stale_hours=48`. Normalization to 0–100 is deferred to the API/display layer (a fixed saturating map `100·raw/(raw+k)` applied at read time): the stored score stays the raw absolute sum, which already sorts via `idx_clusters_momentum` and stays comparable across runs.
**Why this approach:** The defense against "a huge but old story pins the top of the feed" lives in the *shape of the function* (decay), not in *filtering the input*. Because each member's weight halves every 24h, you can safely hand the scorer every member and old ones fade to ~0 on their own — no exclusion logic. **Sum, not mean:** momentum must reward a story that *accumulates* coverage, so the member count has to survive into the score; averaging the weights would flatten "10 fresh articles" and "3 fresh articles" to the same ~1.0 and erase the growth signal. **Pure `(data, knob) → float`:** half-life is a parameter (config-fed at the call site), so the scorer unit-tests without mocking and is defensible on a whiteboard. **Full DB pass, not in-run:** a cluster that received nothing this run still decays and can cross the stale line purely from elapsed time — that transition is invisible to a touched-only pass, so staleness forces sweeping every active cluster. **half-life (24h) < stale window (48h)** by design: at the stale cutoff a member has aged two half-lives and contributes only 0.25, so the score and the stale flag agree instead of contradicting (a 48h half-life would still count a near-dead article at 0.5). **Rejected per-run min-max** (`score / max_this_run`): a cluster's badge would move whenever *other* clusters change, destroying run-to-run comparability and the gaining-vs-fading read — so the 0–100 map is a fixed saturating function at display time, never relative. **Known limitation:** a cluster already marked `stale` is invisible to clustering (which fetches only `active`), so it can't re-absorb new members and revive — a clustering-fetch change left out of momentum's scope.
**Interview angle:** "How does your momentum score stop a huge but old story from permanently pinning the top?" — the decay curve sinks old members, the sum rewards fresh accumulation, and the stale cutoff hard-cuts the tail. Follow-up: "Why recompute clusters that got no new articles?" — staleness is a function of elapsed time, not of an ingestion event, so a touched-only pass would never detect a story going cold.

### 2026-06-21 — Synthesis: purpose-built input model, pure agent, new-clusters-only v1
**What:** Gated LLM briefing (title/summary/so_what) per new cluster via a PydanticAI Anthropic agent (`app/agents/synthesizer.py`). `SynthesisInput`/`SynthesisArticle` are a purpose-built input model that reuses only the vocabulary types (`ArticleSource`, `ArticleDomain`) and carries title/content/source plus the cluster's unioned `key_entities`/`domains` — *not* the `Cluster`/`ArticleInput` objects. `synthesize_cluster` takes a ready `SynthesisInput`; the pipeline assembles it (joins cluster `member_urls` back to the `ArticleInput`s, which still hold the `content` that `EmbeddedArticle` drops). Synthesis runs over `new_clusters` only; results pass to `persist_cluster_result` index-aligned, where the synthesized title overwrites the provisional member-headline and summary/so_what are written in the same insert.
**Why this approach:** The input model is LLM prompt surface — embedding machinery (`centroid`/`vector`/`relevance`) would be noise tokens that degrade output, and embedding `Cluster` would drag clustering internals into the prompt contract. Keeping `synthesize_cluster` as `SynthesisInput → SynthesisOutput` mirrors the classifier (`ArticleInput → ClassificationOutput`) and keeps the agent free of clustering/ingestion coupling; assembly is the pipeline's job. New-clusters-only because they're the only bucket whose member content is in memory this run — `updated` clusters' prior members live only in the DB (a fetch deferred), and singleton `orphans` aren't persisted as clusters. The PRD's "2+ articles" gate arm is already enforced upstream (clustering only emits ≥2-member clusters), so the gate collapsed to "every new cluster." Rejected re-synthesizing `updated` clusters this pass (needs a DB content fetch + prior-summary handling) and resurrecting high-signal orphans as `single_source` clusters (a clustering/persist change) — both flagged as the next slice.
**Interview angle:** "Why a separate input model instead of passing your cluster object to the LLM?" — prompt surface vs internal machinery, decoupling the agent from upstream stages, and how the existing clustering invariant (≥2 members) made half the spec'd gate redundant.

### 2026-06-21 — Synthesis model: Sonnet 4.6 vs Haiku for classification; the env-precedence 404
**What:** Synthesis uses Claude Sonnet 4.6; classification stays on Haiku 4.5. One synthesis call per new cluster, paced by `synthesis_rpm`. Shipping bug: `.env`'s `SYNTHESIS_MODEL` still held the old `google-gla:gemini-2.5-flash`, which overrides the `config.py` default — and since the model-name helper only strips an `anthropic:` prefix, that literal string was sent to the Anthropic API → 404 on every synthesis call while the rest of the pipeline succeeded. Fixed the env value and verified live (15/15 clusters synthesized, 0 failures).
**Why this approach:** Synthesis is the quality-critical surface — the one card the user reads — and runs at low volume (a handful of calls per run), so the marginal cost of the stronger model is small. Classification is high-volume (every fetched article), where Haiku's price dominates, so it stays cheap. Model choice tiers by volume × quality-stakes, not one model everywhere.
**Interview angle:** "How do you pick models across a multi-stage pipeline?" — tier by volume and quality stakes; plus a war story on config precedence (env over code defaults) causing a silent 404 that unit tests missed because they mock the LLM boundary.

### 2026-06-05 — Classifier provider: Gemini Flash-Lite → Claude Haiku 4.5
**What:** Swapped the classification agent to Claude Haiku 4.5 (PydanticAI `AnthropicModel`) and trimmed deps to `pydantic-ai-slim[anthropic]`.
**Why this approach:** Gemini's free tier hit a hard requests-per-day (RPD) wall mid-run; prepaid Claude credits give a controllable hard spend cap, and Haiku is cheap enough (~$0.004/article) for a scheduled pipeline. Rejected padding the prompt past 4,096 tokens to force prompt caching — a hack, and caching silently no-ops below Haiku's cacheable floor.
**Interview angle:** "How did you choose a model and control LLM cost?" — RPM vs RPD limits, prepaid vs metered spend, why caching didn't apply here.

### 2026-06-05 — Dedup before classify (recurring-cost lever)
**What:** The pipeline filters fetched articles against already-persisted `canonical_url`s *before* the classifier runs, and records the skipped count in `pipeline_runs.articles_skipped_known`.
**Why this approach:** Re-classifying the whole pool every run was the dominant recurring cost; dedup-first only classifies the delta (~4–10× cheaper after the cold first run). Rejected cheaper-model / prompt-trimming as smaller levers that also cost quality. Tradeoff: one extra DB read per run (negligible).
**Interview angle:** "Where's the cost in an LLM pipeline and how did you cut it?" — the lever is *what you send*, not *which model*.

### 2026-06-05 — Classifier eval: human-labeled fixture + harness
**What:** A 50-article, class-balanced eval fixture with blind human labels, plus `eval_classifier.py` reporting noise precision/recall, domain overlap, and relevance-band accuracy against fixed targets.
**Why this approach:** Tests prove the code runs; an eval proves the *behavior* is correct. Labeled by hand — not by a model — because the classifier is Claude, so labeling with a Claude model would be circular (shared blind spots). Targets are asymmetric (noise precision ≥0.90 > recall ≥0.75) because a false-positive = dropping a good article, the one failure the product can't afford. Domain uses a deliberately lenient overlap metric (can mask over-tagging) since domain is secondary to the noise gate.
**Interview angle:** "How do you know your classifier is good, and who labeled the ground truth?" — non-circular labeling, metric asymmetry mapped to product cost, and naming the metric's own weakness.

### 2026-06-05 — Taxonomy: removed `culture`; signal = insight, not "technical"
**What:** Dropped the `culture` domain and added a noise rule for nostalgia / retro trivia / standalone quotes, so pure low-substance "interesting" items have no home domain and fall to noise.
**Why this approach:** The eval surfaced that the classifier scored low-substance culture items almost randomly (0.15–0.50). Encoding the editorial stance in the *taxonomy* (no bucket ⇒ noise) is simpler and more consistent than a fuzzy scoring rule. The governing rubric: signal = an actionable insight or fresh perspective, not merely "is it technical" — a business-strategy essay with a real thesis is signal; demoscene nostalgia is not. Rejected a culture-IS-signal rule (an initial misread of the rubric that the eval corrected).
**Interview angle:** "Give an example of your eval changing a design decision." — the eval reversed a taxonomy assumption and tightened the noise definition on real disagreements.
